## 記憶 ETL 估算檢討

### 事件：執行 etl_memory_v2.py（記憶向量化）

**實際結果：**
- 301 個 .md 檔案
- 9,383 chunks（寫入 PostgreSQL）
- 總耗時：~35 分鐘
- 向量嵌入速度：267 chunks/min（CPU 模式）

### 當初估算錯誤的原因

1. **chunks 數量嚴重低估**
   - 我估：~4,000 chunks
   - 實際：9,383 chunks（多了 130%）
   - 主因：用取樣法（10個檔案）推估，忽略了 dreaming 資料夾的檔案會在 ETL 執行期間持續變動/成長

2. **忽略了 embedding 是最大瓶頸**
   - 只算了分詞（~8秒）+ 寫入
   - 忘了向量嵌入才是主要時間消耗

### 正確的估算方式

```
Embedding 時間 ≈ 總 chunks 數量 / (CPU throughput ~267 chunks/分鐘)
```

**下次 ETL 前估算步驟：**
1. 確認所有 .md 檔案的實際大小（`find ... -exec wc -c {} +`）
2. 用 chunking 演算法完整跑一次所有檔案，計算總 chunks 數量
3. 乘以 CPU embedding 速度（~267 chunks/min）
4. 加入分詞+寫入時間（通常 < 2 分鐘）

### 學到的教訓
- 取樣推估只適合變動頻率低的靜態資料
- 進行中的對話日誌（dreaming 資料夾）在 ETL 期間仍會變化，不可用靜態快照估算

## ESP32-S3-Touch-LCD-4B XiaoZhi 韌體燒錄（下午）

### 問題根源
使用者反映「怎麼會出現那種問題，之前不是可以燒錄」，指的是燒錄後 ESP32 一直重啟、出現 `invalid header` 錯誤。

**根本原因：燒錯分區**
- 嘗試燒 `xiaozhi.bin` 到 `0x0`（ bootloader 分區），但這是 app 映像、不是 bootloader
- 正確應該燒到 `ota_0` 分區（`0x100000`）

### 解決方案
1. 用 esptool 直接燒 `xiaozhi.bin` 到 `0x100000`（ota_0 分區）
2. 燒 `ota_data_initial.bin` 到 `0xd000`（otadata 分區）
3. 燒 `partitionsv2-16m.bin` 到 `0x8000`（partition table 分區）

### 燒錄結果
- `xiaozhi.bin`（2869120 bytes）燒到 `0x100000` ✅
- `ota_data_initial.bin`（8192 bytes）燒到 `0xd000` ✅
- `partitionsv2-16m.bin` 燒到 `0x8000` ✅

### 韌體啟動確認
韌體成功啟動，輸出：
```
I (243408) PortfolioApp: 仍在運行... (memory: 7539284 bytes)
```
→ **PortfolioApplication 正在執行中**，確認韌體燒錄成功

### 待確認
- LCD 螢幕是否正常顯示（使用者尚未回傳螢幕照片）
- WiFi 是否成功連線（IoT 路由器密碼待確認）
- Portfolio JSON 是否成功從 R2 抓取並顯示

### 燒錄前置準備（未來參考）
正確燒錄順序：
```
0x8000  → partitionsv2-16m.bin（分區表）
0xd000  → ota_data_initial.bin（otadata）
0x100000 → xiaozhi.bin（ota_0 應用程式）
```

## ESP32 WiFi 掃描功能（2026-07-05 16:56 暫停）

### 目前狀態
- ✅ WiFi 掃描功能正常（找到 CHT Wi-Fi、IoT）
- ✅ 按鈕 callback 正常
- ❌ 列表顯示延遲：掃描結果要等 10 分鐘才出現（timer 太久）
- ❌ Watchdog timeout：FetchPortfolio TLS 失敗一直重試，卡住 LVGL task

### 根本原因
- UpdateTimerCallback 每 10 分鐘才檢查一次 wifi_scan_done_
- FetchPortfolio() TLS handshake 失敗會佔用很長時間
- wifi_scan_done_ 和持股更新綁在同一個 timer，無法分開處理

### 待修方向
1. 把「掃描結果更新」和「持股更新」分開
2. wifi_scan_done_ 改用 one-shot timer 立即觸發
3. FetchPortfolio 失敗時不要 block 太久（加 timeout）
4. 首頁 touch polling crash (331,470) 預防：座標邊界檢查
